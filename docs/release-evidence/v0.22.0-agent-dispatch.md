# Agent Dispatch v0.22.0 Compatibility Evidence

Date: 2026-09-20

Runner: local macOS checkout using a source build from the v0.22.0 candidate
commit (`go build ./cmd/al`). Provider probes ran in an isolated scratch
repository so provider tools could not modify the release checkout. The
scratch repo enabled all five dispatch targets; fresh `init` defaults leave
Antigravity, Grok, and Muse disabled.

## Installed versions

- Claude Code: `2.1.277 (Claude Code)`
- Codex CLI: `codex-cli 0.155.1`
- Antigravity: `1.2.7`
- Grok CLI: `grok 1.0.24 (68e414c661e3) [stable]`
- Muse Code: `Muse Code 1.3.0 (1.3.0-R3401.1)`

`al dispatch options` reported all five providers available. The configured
source-built targets were Codex `gpt-6-astra` with medium reasoning, Claude
`opus[1m]` with high reasoning, Antigravity `gemini-3.8-flash-medium`, Grok
`grok-4.6` with high reasoning, and Muse `muse-spark-1.3` with xhigh
reasoning.

## Fresh and continuation probes

Each reachable provider was to receive a fresh `start`/`wait` probe and a
`continue`/`wait` probe on the same handle. Only Antigravity was reachable;
the other four providers were blocked by external authentication or quota
state before any provider contact attributable to this release.

| Codex | `stout-smooth-jumper` | None | Usage limit: `You've hit your usage limit ... try again at Sep 23rd, 2026 10:14 AM` | Not attempted (fresh blocked) | Blocked by external quota |

| Muse | `loose-swift-optocoupler` | None | Authentication failed: `missing meta credentials: run muse login or set META_API_KEY` | Not attempted (fresh blocked) | Blocked: no Muse credentials in this environment |

Both Antigravity terminal results contained exactly the requested token and
preserved the same provider conversation ID across fresh and continuation
probes, with provider usage evidence on each.

The first Antigravity continuation attempt failed before provider contact
with `dispatch worker was not authorized` (parent/worker gate handshake,
`prelaunch_no_intent`); the session rolled back to the previous invocation
and an immediate retry on the same handle completed with the exact token and
the preserved conversation ID. No code change was involved; recorded here as
an observed transient.

Muse provider stderr also reports `tbh: ignoring unknown top-level member in
settings file ... agentLayerManagedMcpServers`, consistent with the known
`POLICY_MUSE_SELECTIVE_APPROVALS_UNSUPPORTED` warning (Muse 1.3.0 has no
verified native schema for Agent Layer command/MCP allowlists). No Muse
conversation ID or terminal result was available, so this evidence does not
claim Muse end-to-end compatibility beyond the unit-covered paths.

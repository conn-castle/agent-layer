# Historical migration retirement: tentative v1.1.0 implementation plan

Status: expanded cross-subsystem inventory and boundary proposal; inventory completion and independent review gates remain open. This draft changes no implementation or release metadata. No exact preparation version, tag, release dispatch or publication is authorized.

The user's preferred sequence is tentative v1.0.1 correctness fixes first, then historical retirement in tentative v1.1.0. The accepted decision requires projects to finish v1.0.0 conversion before retirement. Installing or pinning a v1.0.0 binary alone does not prove optional adoption completed. Reject unsupported sources and unfinished legacy state before mutation and direct users to finish conversion/recovery using the latest released conversion-capable 1.0.x patch (presently v1.0.0). Preserve user data, imported local edits, normal transactions, crash recovery and immutable published manifests.

All **1.0.x patch releases**, including tentative v1.0.1, remain conversion-capable: retain one-time conversion/adoption executors and compatible recovery throughout that line. Retirement first occurs in the separately authorized 1.1 line. Recovery guidance selects the latest **RELEASED** conversion-capable 1.0.x patch, currently v1.0.0; after a newer supported patch publishes, guide users to it rather than forcing an older patch. A tentative or unpublished version is not a recovery target. The minimum supported prior version remains 1.0.0, independent of which converter patch is recommended.

## Source floor, unknown versions and schema parsing

For the tentative v1.1 retirement contract, the minimum supported prior version is **1.0.0**; a future authorized v1.1.0 migration manifest must declare `min_prior_version: 1.0.0`. That is a planning requirement, not authorization to create/edit that file now.

Resolve and validate installed source evidence before `collectMigrationChain`, `collectMigrationChainFromVersionThroughTarget`, unpinned-trigger chain scans, operation scheduling, or any filesystem/config/journal/snapshot/recovery mutation. A read-only load of the target contract is permitted. Validate the entire proposed execution plan before its first operation; a late unsupported-kind error after earlier operations is unacceptable.

- Known installed source below 1.0.0: reject before chain collection with guidance to use the latest released conversion-capable 1.0.x patch to complete conversion/recovery, then retry. Do not silently skip old operations and continue.
- Known source at/above 1.0.0: validate consistency with installed evidence and separately reject unfinished flat skills, old instruction slots, mixed conversion or adoption-v2 recovery. A version pin identifies a version; it never proves conversion completed.
- Installed source missing, unknown, unpinned, malformed or conflicting: fail closed before chain collection/mutation with explicit diagnostic and latest released conversion-capable 1.0.x assessment/conversion guidance. Do not infer 1.0.0 from the target, silently use `targetManifest.MinPriorVersion` as the source, or run source-agnostic historical operations. Restoring a valid pin alone is insufficient; conversion/recovery state must also be checked.
- A positively identified new installation without installed project artifacts follows ordinary fresh-install behavior, not the unknown installed-source migration fallback. Define and fixture that distinction so an existing installation with a missing pin cannot be mistaken for fresh work.

Separate schema recognition from execution support. `validateUpgradeMigrationOperation` must continue accepting recognized historical kinds and validating their fields, including `migrate_skills_format` in published `0.9.0.json` and the `claim_skill_projection_roots` record. Removing an executor is not permission to remove a schema kind or rewrite historical JSON. Structural loaders/tooling still parse those byte-identical documents. Source/plan validation rejects an attempt to execute a retired operation with unsupported-source/state guidance before any operation runs; unknown schema kinds remain structural errors.

## Implementation order

1. Land/review the tentative v1.0.1 correctness work first, keeping all 1.0.x conversion/recovery capabilities intact. Obtain exact retirement preparation-version authorization before editing any versioned contract; no tag, release workflow change or publication is included.
2. Complete the broad source inventory and record per-path decisions/fixtures, then finish independent boundary review. Incorporate accepted material plan findings and complete independent boundary review before implementation.
3. Implement read-only source/floor and unfinished-state checks before chain collection or mutation. Replace unknown-source fallback and prove refusal leaves all state unchanged.
4. Remove historical execution and execution-only tests, retaining recognized schema kinds, normal transaction recovery/locking APIs, native-cache preservation and other justified ongoing compatibility behavior.
5. Prepare only the authorized new contract and the concrete docs/site/script surfaces above. Preserve published manifests and historical changelog/release evidence byte-identically.
6. Run the behavioral fixtures and upgrade-contract checks above, then full `make ci`. Obtain independent code review of actual implementation and resolve material findings before moving the draft to ready for review.
